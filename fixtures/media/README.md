# PNG and JPEG decoder fixtures

These tiny files exercise the native image decoders at milestone M4. They are
committed because they are a few hundred bytes to a few kilobytes each, not
model-scale data. They are not official image-preprocessing or embedding
goldens.

## Provenance

### PNG inputs

The original PNG inputs were generated outside the product with Python 3
standard-library modules only (struct, zlib, hashlib). No third-party image
library, external decoder, or network access was used. The generator computed
PNG chunks, CRCs, per-row filters, zlib compression, and Adler-32 checksums
directly.

- rgb_2x2.png: RGB8, row filters None and Sub, fixed-Huffman zlib block.
- rgba_2x2.png: RGBA8, row filters None and Paeth, fixed-Huffman zlib block.
- gray_2x2.png: grayscale8, row filters Average and Up, fixed-Huffman zlib
  block.
- gradient_16x16.png: RGB8, all rows filter None, dynamic-Huffman zlib block.
- quadrants_16x16.png: RGB8, four color quadrants, all rows filter None,
  dynamic-Huffman zlib block. Generated with the same Python standard-library
  procedure.
- wide_32x16.png and tall_16x32.png: RGB8 aspect-ratio fixtures, all rows
  filter None, generated with the same Python standard-library procedure.
- quadrants_16x16_rot90.png and quadrants_16x16_rot180.png: RGB8 rotations of
  quadrants_16x16.png, generated by permuting its decoded pixels with Python
  standard-library code.

The rotation and aspect-ratio PNGs were added for the M4 preprocessing
coverage. They exercise non-square target sizes and rotations without changing
the decoder fixture set.

### JPEG inputs and references

The JPEG files were generated outside the product from the committed PNG or
PPM inputs:

- rgb_2x2.jpg, gradient_16x16.jpg, and quadrants_16x16.jpg were produced with
  macOS sips 316 from the corresponding PNG files at JPEG quality 90.
- gray_2x2.jpg was produced with cjpeg 3.1.0 (libjpeg-turbo) in grayscale mode
  from a two-by-two PGM with values 0, 64, 128, 255.
- quadrants_16x16_444.jpg was produced with cjpeg 3.1.0 at quality 90 and
  sampling 1x1 from a PPM generated by the Python standard-library procedure.

The five *_ref.png files were rendered by macOS sips 316 from the JPEG files.
They are independent reference decodes used only by tests; the product never
runs sips, cjpeg, or djpeg. These tools are laboratory-only.

## Expected decoder output

PNG:

- rgb_2x2: row 0 red, green; row 1 blue, white.
- rgba_2x2: row 0 opaque red, half-transparent green; row 1 quarter-alpha
  blue, transparent white.
- gray_2x2: row 0 values 0, 64; row 1 values 128, 255.
- gradient_16x16: pixel (x, y) is (17x, 17y, 8(x + y)) modulo 256.
- quadrants_16x16: four 8x8 quadrants with red, green, blue, and neutral
  gradients.

JPEG (native decoder, approximate because JPEG is lossy):

- gray_2x2: 2x2 grayscale, decoded bytes approximately 0, 72, 136, 252.
- rgb_2x2: 2x2 RGB, decoded bytes approximately (75, 75, 75), (151, 151, 151),
  (30, 30, 30), (254, 254, 254). The 4:2:0 chroma is averaged across the four
  pixels, so the original red/green/blue/white pattern becomes neutral.
- gradient_16x16: 16x16 RGB; pixel (x, y) is approximately
  (17x, 17y, 8(x + y)) modulo 256, with JPEG and bilinear-chroma differences.
- quadrants_16x16: 16x16 RGB with four color quadrants and bilinear chroma
  transitions near the edges.
- quadrants_16x16_444: 16x16 RGB with four color quadrants and direct 4:4:4
  chroma, close to the source pixels.

The tests compare JPEG output against the committed reference PNGs with
per-byte tolerances: 2 for grayscale, 4 for rgb_2x2, 3 for the 4:4:4 fixture,
and 24 for the 4:2:0 fixtures with sharp color edges. The tolerances cover
decoder IDCT and bilinear-upsampling differences; dimensions, channel counts,
and corruption behavior are exact.

## Regeneration contract

Any replacement fixture must record its size, SHA-256, dimensions, color type
or JPEG sampling factors, row filters or JPEG marker structure, and the exact
generation procedure here. PNG inputs must remain reproducible with the same
standard-library-only procedure. JPEG inputs must remain reproducible from the
committed PNG/PPM inputs with the documented sips or cjpeg invocation, and the
reference PNG must be rendered by an independent decoder. Corrupted variants
are generated inside Rust tests by truncating or mutating these files; they are
not committed.

## Image preprocessing goldens

fixtures/media/preprocess_golden.json records the official preprocessing output
for nine images. It is committed because the reference path is expensive to
reproduce and because the Rust tests enforce exact equality.

### Provenance

Generated outside the product on 2026-11-11 with Python 3.13, PyTorch 2.15.0
CPU, and Transformers 5.22.2 in float32, using
scripts/generate_image_goldens.py. The official Gemma4ImageProcessor depends
on torchvision, which was not installed in the reference environment, so the
generator reproduces the same tensor operations directly:

- grayscale replication and RGBA compositing over white with half-to-even
  rounding;
- aspect-ratio preserving target size;
- torch.nn.functional.interpolate with mode bicubic, antialias true, and
  align_corners false on uint8 tensors;
- rescaling by 1/255, patchification, and padded positions.

### Regeneration contract

The generator must be run only outside the product, with the frozen model cache
and the reference environment. A replacement fixture must record the same
fields, the generator version, the PyTorch and Transformers versions, and the
new SHA-256. The Rust tests compare resized bytes, padded patch values, and
positions exactly; no tolerance is accepted for preprocessing.
